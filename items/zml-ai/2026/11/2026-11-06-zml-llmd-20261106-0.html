Asynchronous scheduling beta

We have added asynchronous scheduling to Llama and Gemma 4. The idea is simple: while the accelerator is running one step, the CPU can prepare the next one. Less time waiting between steps.

You can enable it with --async-scheduling. It is opt-in for now. Speculative decoding still uses the synchronous path, and Llama’s asynchronous path also works with data parallelism. The next release should bring more models on board.

This is in beta. Once we are satisfied with the performance and stability, we will make it the default.

Data parallelism beta

Llama now supports --data-parallel. This distributes requests and their KV caches across groups of devices. We also improved weight sharding for this configuration to reduce communication between those groups.

For example, --data-parallel=2 splits the work across two groups.

On 2×RTX 5090, our Llama development benchmark went from 700 to 1,600 tok/s with --data-parallel=2, --batch-size=16 and --token-batch-size=256. That’s a 2.3× improvement to the data-parallel path. The same benchmark with --data-parallel=1 stays at roughly 2,000 tok/s, so the best configuration still depends on the workload.

This is still in beta.

Faster LFM 3

Last week, we brought LFM 3 to zml/llmd. This week, we improved how its embeddings are sharded across devices, which improves throughput when running it on multiple GPUs.

Serving improvements

A few fixes also made it into this release:

  • Cache hits are now reported in API usage responses through prompt_tokens_details.cached_tokens.
  • Prompts that exceed the context limit return HTTP 400 with context_length_exceeded. Unsupported response_format values also return HTTP 400.
  • When enable_thinking is omitted, we now respect the model’s default. This fixes Gemma 4’s default behaviour.
  • We fixed KV-cache matching in LFM 2 and an issue with grouped-weight packing.
  • Tini is now the default entrypoint for all zml/llmd container images, which should improve signal handling and shutdown behaviour.
