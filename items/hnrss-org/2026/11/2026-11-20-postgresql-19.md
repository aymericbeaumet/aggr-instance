## E.1. Release 19 [#](https://www.postgresql.org/docs/19/#RELEASE-19)

**Release date:** ;2026-11-19

### E.1.1. Overview [#](https://www.postgresql.org/docs/19/#RELEASE-19-HIGHLIGHTS)

PostgreSQL 19 contains many new features and enhancements, including:

- New [REPACK](https://www.postgresql.org/docs/19/sql-repack.html "REPACK") command that reclaims disk space and reorganizes table contents, which can improve query performance. `REPACK (CONCURRENTLY)` allows repacking without blocking reads and writes to the table.

- [pg\_plan\_advice](https://www.postgresql.org/docs/19/pgplanadvice.html "F.30. pg_plan_advice — help the planner get the right plan") extension for controlling query planner decisions and [pg\_stash\_advice](https://www.postgresql.org/docs/19/pgstashadvice.html "F.33. pg_stash_advice — store and automatically apply plan advice") extension that applies plan advice automatically based on the query.

- Better performance in many areas, including automatic scaling of the number of I/O worker processes, quicker foreign-key checks, and further planning and execution optimizations.

- Logical replication can now be enabled without a server restart when [wal\_level](https://www.postgresql.org/docs/19/runtime-config-wal.html#GUC-WAL-LEVEL) is set to `replica`.

- Logical replication of [sequence values](https://www.postgresql.org/docs/19/logical-replication-sequences.html "29.7. Replicating Sequences").

- Support for “read-your-writes” consistency on standbys via the new [WAIT](https://www.postgresql.org/docs/19/sql-wait.html "WAIT") command.

- [Parallel autovacuum of table indexes](https://www.postgresql.org/docs/19/runtime-config-vacuum.html#GUC-AUTOVACUUM-MAX-PARALLEL-WORKERS) and [autovacuum prioritization](https://www.postgresql.org/docs/19/routine-vacuuming.html#AUTOVACUUM-PRIORITY "24.1.6.1. Autovacuum Prioritization") through a new scoring system.

The above items and other new features of PostgreSQL 19 are explained in more detail in the sections below.

### E.1.2. Migration to Version 19 [#](https://www.postgresql.org/docs/19/#RELEASE-19-MIGRATION)

A dump/restore using [pg\_dumpall](https://www.postgresql.org/docs/19/app-pg-dumpall.html "pg_dumpall") or use of [pg\_upgrade](https://www.postgresql.org/docs/19/pgupgrade.html "pg_upgrade") or logical replication is required for those wishing to migrate data from any previous release. See [Section 18.6](https://www.postgresql.org/docs/19/upgrading.html "18.6. Upgrading a PostgreSQL Cluster") for general information on migrating to new major releases.

Version 19 contains a number of changes that may affect compatibility with previous releases. Observe the following incompatibilities:

- Add server variable [`password_expiration_warning_threshold`](https://www.postgresql.org/docs/19/runtime-config-connection.html#GUC-PASSWORD-EXPIRATION-WARNING-THRESHOLD) to warn about password expiration (Gilles Darold, Nathan Bossart) [§](https://postgr.es/c/1d92e0c2c)

  The default warning period is seven days.

- Issue a warning after successful MD5 password authentication (Nathan Bossart) [§](https://postgr.es/c/bc60ee860)

  The warning can be disabled via server variable [`md5_password_warnings`](https://www.postgresql.org/docs/19/runtime-config-connection.html#GUC-MD5-PASSWORD-WARNINGS). MD5 passwords were marked as deprecated in PostgreSQL 18.

- Remove RADIUS support (Thomas Munro) [§](https://postgr.es/c/a1643d40b)

  PostgreSQL only supported RADIUS over UDP, which is unfixably insecure.

- Force [`standard_conforming_strings`](https://www.postgresql.org/docs/19/runtime-config-compatible.html#GUC-STANDARD-CONFORMING-STRINGS) to always be `on` in the database server (Tom Lane) [§](https://postgr.es/c/457620845)

  Dumps created using pre-PostgreSQL 19 versions of [pg\_dump](https://www.postgresql.org/docs/19/app-pgdump.html "pg_dump") or [pg\_dumpall](https://www.postgresql.org/docs/19/app-pg-dumpall.html "pg_dumpall"), and using `standard_conforming_strings = off`, will not properly load into PostgreSQL 19 and later servers. Users should create dumps using PostgreSQL 19 or later versions of these applications, or use `standard_conforming_strings = on`.

  Client applications still support operations with servers having `standard_conforming_strings = off`, for compatibility with old servers. The server variable `escape_string_warning` has been removed as unnecessary.

- Disallow carriage returns and line feeds in database, role, and tablespace names (Mahendra Singh Thalor) [§](https://postgr.es/c/b380a56a3)

  [pg\_upgrade](https://www.postgresql.org/docs/19/pgupgrade.html "pg_upgrade") will also disallow upgrading of clusters that use such names. This was changed to avoid security problems.

- Change the default index opclasses for [`inet`](https://www.postgresql.org/docs/19/datatype-net-types.html "8.9. Network Address Types") and [`cidr`](https://www.postgresql.org/docs/19/datatype-net-types.html "8.9. Network Address Types") data types from [btree\_gist](https://www.postgresql.org/docs/19/btree-gist.html "F.8. btree_gist — GiST operator classes with B-tree behavior") to [GiST](https://www.postgresql.org/docs/19/gist.html "65.2. GiST Indexes") (Tom Lane) [§](https://postgr.es/c/b3b0b4571) [§](https://postgr.es/c/b352d3d80)

  The [btree\_gist](https://www.postgresql.org/docs/19/btree-gist.html "F.8. btree_gist — GiST operator classes with B-tree behavior") `inet`/`cidr` opclasses are broken because they can exclude rows that should be returned. [pg\_upgrade](https://www.postgresql.org/docs/19/pgupgrade.html "pg_upgrade") will disallow upgrading of clusters with [btree\_gist](https://www.postgresql.org/docs/19/btree-gist.html "F.8. btree_gist — GiST operator classes with B-tree behavior") `inet`/`cidr` indexes.

- Disallow system columns from being used in [`COPY FROM ... WHERE`](https://www.postgresql.org/docs/19/sql-copy.html "COPY") (Tom Lane) [§](https://postgr.es/c/21c69dc73)

  The values of such columns were not well-defined.

- Change a [`json_array()`](https://www.postgresql.org/docs/19/functions-json.html "9.17. JSON Functions and Operators") call which returns no rows to return an empty JSON array (Richard Guo) [§](https://postgr.es/c/8d829f5a0)

  This previously returned `NULL`.

- Cause transactions to pass their `READ ONLY` and `DEFERRABLE` status to [postgres\_fdw](https://www.postgresql.org/docs/19/postgres-fdw.html "F.40. postgres_fdw — access data stored in external PostgreSQL servers") sessions (Etsuro Fujita) [§](https://postgr.es/c/de28140de)

  This means `READ ONLY` transactions can no longer modify rows processed by [postgres\_fdw](https://www.postgresql.org/docs/19/postgres-fdw.html "F.40. postgres_fdw — access data stored in external PostgreSQL servers") sessions.

- Change default of [`max_locks_per_transaction`](https://www.postgresql.org/docs/19/runtime-config-locks.html#GUC-MAX-LOCKS-PER-TRANSACTION) from 64 to 128 (Heikki Linnakangas) [§](https://postgr.es/c/79534f906)

  Lock size allocation has changed, so effectively settings must now be doubled to match their capacity in previous releases.

- Remove server variable `io_workers` (Thomas Munro) [§](https://postgr.es/c/d1c01b79d)

  This has been replaced by four new variables; see [Section E.1.3.1.2](https://www.postgresql.org/docs/19/release-19.html#RELEASE-19-PERFORMANCE "E.1.3.1.2. General Performance").

- Change [JIT](https://www.postgresql.org/docs/19/jit.html "Chapter 30. Just-in-Time Compilation (JIT)") to be disabled by default (Jelte Fennema-Nio) [§](https://postgr.es/c/7f8c88c2b)

  Previously JIT was enabled by default, and activated based on optimizer costs, but this costing has been determined to be unreliable. This change requires sites that are doing many large analytical queries to manually enable JIT.

- Change [parallel vacuum](https://www.postgresql.org/docs/19/routine-vacuuming.html#PARALLEL-VACUUM "24.1.7. Parallel Vacuum") leaders and workers to share the cost-based vacuum delay limit (Bharath Rupireddy) [§](https://postgr.es/c/8628df889)

  Previously each worker process slept based only on the cost it incurred itself, so a parallel vacuum could consume several times the budget set by [`vacuum_cost_limit`](https://www.postgresql.org/docs/19/runtime-config-vacuum.html#GUC-VACUUM-COST-LIMIT). With this change, [`VACUUM`](https://www.postgresql.org/docs/19/sql-vacuum.html "VACUUM") with parallel workers and cost-based delay enabled might run slower than in previous releases.

- Rename column `sync_error_count` to `sync_table_error_count` in system view [`pg_stat_subscription_stats`](https://www.postgresql.org/docs/19/monitoring-stats.html#PG-STAT-SUBSCRIPTION-STATS "Table 27.20. pg_stat_subscription_stats View") (Vignesh C) [§](https://postgr.es/c/3edaf29fa)

  This is necessary since sequence errors are now tracked separately.

- Rename wait event *type* `BUFFERPIN` to `BUFFER` and rename wait event `BufferPin` to `BufferCleanup` (Andres Freund) [§](https://postgr.es/c/6c5c393b7)

- Remove wait event `BufferContent` and add more precise wait events `BufferShared`, `BufferShareExclusive`, and `BufferExclusive` (Andres Freund) [§](https://postgr.es/c/fcb9c977a)

- Change index access method handlers to use a static [`IndexAmRoutines`](https://www.postgresql.org/docs/19/indexam.html "Chapter 63. Index Access Method Interface Definition") structure, rather than dynamically allocated ones (Matthias van de Meent) [§](https://postgr.es/c/bc6374cd7)

- Remove optimizer hook get\_relation\_info\_hook and add better-placed hook build\_simple\_rel\_hook (Robert Haas) [§](https://postgr.es/c/91f33a2ae)

- Change [psql](https://www.postgresql.org/docs/19/app-psql.html "psql")'s `\crosstabview` command to honor the `\pset null` setting (Chao Li) [§](https://postgr.es/c/4df5fe383)

- Change [full text search](https://www.postgresql.org/docs/19/textsearch.html "Chapter 12. Full Text Search") and [pg\_trgm](https://www.postgresql.org/docs/19/pgtrgm.html "F.37. pg_trgm — support for similarity of text using trigram matching") to use the database's locale provider for character classification when parsing text (Jeff Davis) [§](https://postgr.es/c/e113f9c102b)

  Previously, characters were classified using libc, regardless of the locale provider. In databases with a locale provider other than libc (e.g., `ICU`, `builtin`) and where the locale configured through that locale provider behaves differently from the `LC_CTYPE` setting configured for the database, particularly a LC\_CTYPE of `C`, the output of some full text search and pg\_trgm functions could change. When upgrading such databases using [pg\_upgrade](https://www.postgresql.org/docs/19/pgupgrade.html "pg_upgrade"), it is recommended to reindex all indexes which use full text search and pg\_trgm after the upgrade, and to recompute any stored `tsvector` values.

- Change how [fuzzystrmatch](https://www.postgresql.org/docs/19/fuzzystrmatch.html "F.16. fuzzystrmatch — determine string similarities and distance") functions handle non-ASCII characters (Peter Eisentraut, Jeff Davis) [§](https://postgr.es/c/e39ece034) [§](https://postgr.es/c/b96a9fd76f3)

  `dmetaphone()` and `dmetaphone_alt()` now upper-case their input using the database's default collation rather than always using libc, and `soundex()`, `metaphone()`, and `difference()` now treat only ASCII letters as letters. When upgrading with [pg\_upgrade](https://www.postgresql.org/docs/19/pgupgrade.html "pg_upgrade"), it is recommended to reindex any indexes that use these functions after the upgrade.

- Remove `MULE_INTERNAL` encoding (Thomas Munro) [§](https://postgr.es/c/77645d44e)

  This encoding was complex and rarely used. Databases using it will need to be dumped and restored with a different encoding.

### E.1.3. Changes [#](https://www.postgresql.org/docs/19/#RELEASE-19-CHANGES)

Below you will find a detailed account of the changes between PostgreSQL 19 and the previous major release.

#### E.1.3.1. Server [#](https://www.postgresql.org/docs/19/#RELEASE-19-SERVER)

##### E.1.3.1.1. Optimizer [#](https://www.postgresql.org/docs/19/#RELEASE-19-OPTIMIZER)

- Allow `NOT IN` clauses to be converted to more efficient `ANTI JOIN`s when NULLs are not present (Richard Guo) [§](https://postgr.es/c/383eb21eb)

- Allow more `LEFT JOIN`s to be converted to `ANTI JOIN`s (Tender Wang, Richard Guo) [§](https://postgr.es/c/cf74558fe)

- Allow use of Memoize for `ANTI JOIN`s with unique inner sides (Richard Guo) [§](https://postgr.es/c/0da29e4cb)

- Allow some aggregate processing to be performed before joins (Richard Guo, Antonin Houska) [§](https://postgr.es/c/8e1185910) [§](https://postgr.es/c/bd94845e8) [§](https://postgr.es/c/3a08a2a8b)

  This can reduce the number of rows needed to be processed.

- Improve hash join's handling of tuples with `NULL` join keys (Tom Lane) [§](https://postgr.es/c/1811f1af9)

- Improve the planning of semijoins (Richard Guo) [§](https://postgr.es/c/24225ad9a)

- Allow Append and MergeAppend to consider explicit incremental sorts (Richard Guo) [§](https://postgr.es/c/55a780e94)

- Convert [`IS [NOT] DISTINCT FROM NULL`](https://www.postgresql.org/docs/19/functions-comparison.html#FUNCTIONS-COMPARISON-PRED-TABLE "Table 9.2. Comparison Predicates") to `IS [NOT] NULL` during constant folding (Richard Guo) [§](https://postgr.es/c/f41ab5157)

  The latter form is more easily optimized.

- Simplify [`IS [NOT] DISTINCT FROM`](https://www.postgresql.org/docs/19/functions-comparison.html#FUNCTIONS-COMPARISON-PRED-TABLE "Table 9.2. Comparison Predicates") to equality/inequality operators when inputs are proven non-nullable (Richard Guo) [§](https://postgr.es/c/0a3796125)

- Perform earlier constant folding of *`var`* `IS [NOT] NULL` in the optimizer (Richard Guo) [§](https://postgr.es/c/e2debb643)

  This allows for later optimizations.

- Simplify [`COALESCE()`](https://www.postgresql.org/docs/19/functions-conditional.html#FUNCTIONS-COALESCE-NVL-IFNULL "9.19.2. COALESCE") and `ROW(...) IS [NOT] NULL` to avoid evaluating unnecessary arguments (Richard Guo) [§](https://postgr.es/c/10c4fe074) [§](https://postgr.es/c/cb7b7ec7a)

- Simplify `IS [NOT] TRUE/FALSE/UNKNOWN` to plain boolean expressions when the input is proven non-nullable (Richard Guo) [§](https://postgr.es/c/0aaf0de7f)

- Speed up join selectivity computations for large optimizer statistics targets (Ilia Evdokimov, David Geier) [§](https://postgr.es/c/057012b20)

- Add proper optimizer statistics for functions returning boolean values (Tom Lane) [§](https://postgr.es/c/1eccb9315)

- Allow [extended statistics](https://www.postgresql.org/docs/19/sql-createstatistics.html "CREATE STATISTICS") on virtual generated columns (Yugo Nagata) [§](https://postgr.es/c/f7f4052a4)

- Allow function [`pg_restore_extended_stats()`](https://www.postgresql.org/docs/19/functions-admin.html#FUNCTIONS-ADMIN-STATSMOD "Table 9.106. Database Object Statistics Manipulation Functions") to restore optimizer extended statistics (Corey Huinker, Michael Paquier, Chao Li) [§](https://postgr.es/c/0e80f3f88) [§](https://postgr.es/c/302879bd6) [§](https://postgr.es/c/efbebb4e8) [§](https://postgr.es/c/ba97bf9cb)

- Add function [`pg_clear_extended_stats()`](https://www.postgresql.org/docs/19/functions-admin.html#FUNCTIONS-ADMIN-STATSMOD "Table 9.106. Database Object Statistics Manipulation Functions") to remove extended statistics (Corey Huinker, Michael Paquier) [§](https://postgr.es/c/d756fa101)

- Adjust the optimizer to consider startup costs of partial paths (Robert Haas, Tomas Vondra) [§](https://postgr.es/c/8300d3ad4)

- Allow negative values of [`pg_aggregate`](https://www.postgresql.org/docs/19/catalog-pg-aggregate.html "52.2. pg_aggregate").[`aggtransspace`](https://www.postgresql.org/docs/19/catalog-pg-aggregate.html "52.2. pg_aggregate") to indicate unbounded memory usage (Richard Guo) [§](https://postgr.es/c/185e30426)

  This information is used by the optimizer in planning memory usage.

##### E.1.3.1.2. General Performance [#](https://www.postgresql.org/docs/19/#RELEASE-19-PERFORMANCE)

- Improve performance of foreign key constraint checks (Junwang Zhao, Amit Langote, Chao Li) [§](https://postgr.es/c/2da86c1ef) [§](https://postgr.es/c/e484b0eea)

- Improve [asynchronous I/O](https://www.postgresql.org/docs/19/runtime-config-resource.html#GUC-IO-METHOD) read-ahead scheduling for large requests (Andres Freund) [§](https://postgr.es/c/a9ee66881) [§](https://postgr.es/c/8ca147d58) [§](https://postgr.es/c/f63ca3379)

- Allow [`io_method`](https://www.postgresql.org/docs/19/runtime-config-resource.html#GUC-IO-METHOD) method `worker` to automatically control needed background workers (Thomas Munro) [§](https://postgr.es/c/d1c01b79d)

  The new server variables are [`io_min_workers`](https://www.postgresql.org/docs/19/runtime-config-resource.html#GUC-IO-MIN-WORKERS), [`io_max_workers`](https://www.postgresql.org/docs/19/runtime-config-resource.html#GUC-IO-MAX-WORKERS), [`io_worker_idle_timeout`](https://www.postgresql.org/docs/19/runtime-config-resource.html#GUC-IO-WORKER-IDLE-TIMEOUT), and [`io_worker_launch_interval`](https://www.postgresql.org/docs/19/runtime-config-resource.html#GUC-IO-WORKER-LAUNCH-INTERVAL).

- Allow query table scans to mark pages as all-visible in the [visibility map](https://www.postgresql.org/docs/19/routine-vacuuming.html#VACUUM-FOR-VISIBILITY-MAP "24.1.4. Updating the Visibility Map") (Melanie Plageman) [§](https://postgr.es/c/b46e1e54d)

  Previously only [`VACUUM`](https://www.postgresql.org/docs/19/sql-vacuum.html "VACUUM") and [`COPY ... FREEZE`](https://www.postgresql.org/docs/19/sql-copy.html "COPY") could do this.

- Allow [autovacuum](https://www.postgresql.org/docs/19/routine-vacuuming.html#AUTOVACUUM "24.1.6. The Autovacuum Daemon") to use [`parallel autovacuum workers`](https://www.postgresql.org/docs/19/sql-createtable.html#RELOPTION-AUTOVACUUM-PARALLEL-WORKERS) (Daniil Davydov) [§](https://postgr.es/c/1ff3180ca) [§](https://postgr.es/c/2a3d2f9f6)

  The maximum number of workers is controlled by server variable [`autovacuum_max_parallel_workers`](https://www.postgresql.org/docs/19/runtime-config-vacuum.html#GUC-AUTOVACUUM-MAX-PARALLEL-WORKERS) and per-table storage parameter `autovacuum_parallel_workers`.

- Allow [`TID`](https://www.postgresql.org/docs/19/datatype-oid.html "8.19. Object Identifier Types") Range Scans to be parallelized (Cary Huang, David Rowley) [§](https://postgr.es/c/0ca3b1697)

- Improve [`COPY FROM`](https://www.postgresql.org/docs/19/sql-copy.html "COPY") performance for text and CSV input using SIMD CPU instructions (Nazir Bilal Yavuz, Shinya Kato) [§](https://postgr.es/c/e0a3a3fd5)

- Improve [`NOTIFY`](https://www.postgresql.org/docs/19/sql-notify.html "NOTIFY") to only wake up backends that are listening to specified notifications (Joel Jacobson) [§](https://postgr.es/c/282b1cde9)

  Previously most backends were woken by [`NOTIFY`](https://www.postgresql.org/docs/19/sql-notify.html "NOTIFY").

- Change [`wal_compression`](https://www.postgresql.org/docs/19/runtime-config-wal.html#GUC-WAL-COMPRESSION) equals `on` to use the best WAL compression method available (wenhui qiu) [§](https://postgr.es/c/5838806ce)

  Previously this always used `pglz`.

- Change the default [TOAST](https://www.postgresql.org/docs/19/storage-toast.html "66.2. TOAST") compression method from `pglz` to the more efficient `lz4` (Euler Taveira) [§](https://postgr.es/c/34dfca293)

  This is done by changing the default for server variable [`default_toast_compression`](https://www.postgresql.org/docs/19/runtime-config-client.html#GUC-DEFAULT-TOAST-COMPRESSION).

- Improve performance of internal row deformation (David Rowley) [§](https://postgr.es/c/c456e3911)

- Improve performance of repeated UTF-8 case-folding operations (Andreas Karlsson) [§](https://postgr.es/c/c4ff35f10)

- Improve performance of hash index bulk-deletion and [`GIN`](https://www.postgresql.org/docs/19/gin.html "65.4. GIN Indexes") index vacuuming using streaming reads (Xuneng Zhou) [§](https://postgr.es/c/bfa3c4f10) [§](https://postgr.es/c/6c228755a)

- Improve sort performance using radix sort (John Naylor) [§](https://postgr.es/c/ef3c3cf6d)

- Improve timing performance measurements (Lukas Fittl, Andres Freund, David Geier) [§](https://postgr.es/c/294520c44) [§](https://postgr.es/c/16fca4825)

  This benefits [`EXPLAIN (ANALYZE, TIMING)`](https://www.postgresql.org/docs/19/sql-explain.html "EXPLAIN") and [pg\_test\_timing](https://www.postgresql.org/docs/19/pgtesttiming.html "pg_test_timing"), and is controlled via server variable [`timing_clock_source`](https://www.postgresql.org/docs/19/runtime-config-resource.html#GUC-TIMING-CLOCK-SOURCE).

- Optimize [plpgsql](https://www.postgresql.org/docs/19/plpgsql.html "Chapter 41. PL/pgSQL — SQL Procedural Language") syntax `SELECT simple-expression INTO` *`var`* (Tom Lane) [§](https://postgr.es/c/ce8d5fe0e)
