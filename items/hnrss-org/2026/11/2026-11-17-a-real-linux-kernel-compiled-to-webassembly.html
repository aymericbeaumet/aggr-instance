A real Linux kernel, compiled to WebAssembly. It boots to a shell in less than a second.

Try it · Performance · Features · CLI · How it works · Benchmarks · JavaScript SDK

unkernel is Linux 7.x built as a single wasm module with a real MMU. The kernel (syscalls, scheduler, memory management, ext4, TCP/IP) is compiled code, not emulated, so programs get Linux's own behavior down to the edge cases. Only user programs are emulated: unmodified aarch64 (arm64) Linux binaries, so Alpine and Debian packages run as they are.

Open a page and you have a Linux machine with a shell, a package manager, a persistent disk, internet access, and a screen with sound. It runs entirely on your device, with nothing to install and no server, and every layer is open source. How it works explains the design.

⚡ Performance

Much of what makes a system feel slow lives in the kernel: starting processes, syscalls, page faults, file and network I/O. In unkernel that path runs at wasm speed.

  • Boot: the kernel reaches /init about 70 ms after it starts, and the Alpine prompt appears 0.3 s after node launches. The page downloads about 10 MB, and Alpine boots in 48 MiB of guest memory.
  • Syscalls at close to native cost: getppid takes about 170 ns (110 native, 1.7 µs under qemu-system), a 64-byte read about 170 ns (160 native).
  • fork at native speed: fork + exit + wait takes about 60 µs, against about 70 µs natively and 1.2 ms under qemu-system.
  • A JIT for user code: hot aarch64 code, including the AES, PMULL and SHA instructions OpenSSL uses, is compiled to wasm while it runs. With it a shell loop runs 1.6 times and sort 2.3 times as fast as on the interpreter alone, and OpenSSL in the guest does AES-128-GCM at about 100 MB/s and SHA-256 at about 160 MB/s.

The syscall and fork numbers were measured on 2026-11-14 (with the riscv64 user space the project started with; the path through the kernel is the same), the JIT numbers on 2026-11-18. CPU-heavy programs are well behind native: apk search over the main index takes about 0.8 s, apk add python3 about 3.4 s. Benchmarks has the full numbers.

Anything a program relies on, from /proc and epoll to cgroups and overlayfs, behaves as it does on a server, because it runs the same code.

  • A real MMU (arch/wasm with Sv39 page tables): fork, mmap, copy-on-write, shared memory, threads and signals behave as they do on hardware. This is not a NOMMU port where programs are limited to vfork.
  • Linux's own file systems: ext4, overlayfs, tmpfs, loop devices, FUSE, and 9p, which mounts file systems your program serves from the host. The root file system is an overlay: a read-only distro image under your changes, which go to a persistent ext4 disk, so everything you change survives a reload, and a safe mode recovers a system you broke.
  • Linux's own TCP/IP stack, with DHCP and DNS, reaching the internet through your host's sockets or a Wisp proxy (Add a network).
  • cgroups, namespaces, userfaultfd, fanotify and TUN: enough for systemd to boot Ubuntu 26.10 to multi-user.target.
  • Devices: a framebuffer (/dev/fb0), evdev keyboard, mouse and touch, sound through ALSA and /dev/dsp, AF_VSOCK, and shared memory with the host.
  • aarch64 user space: ARMv8.0-A with FP and AdvSIMD plus the AES, PMULL, SHA1, SHA2, SHA512, SHA3, CRC32 and LSE atomics extensions, so distribution binaries and OpenSSL's hardware AES, GHASH and SHA paths run unchanged. aarch64 is a first-class port of every distribution, so their full, current package archives are available.

Known limits lists what is still missing.

🧰 What you can do with it

  • Carry a Linux shell anywhere. Alpine Linux 3.24 runs in Chrome, Edge, Firefox and Safari, including on phones. Install anything with apk add from Alpine's regular mirrors. Type a command that isn't installed, such as htop, and its package is installed for you. apk starts with only the main repository, because it is about 4x faster that way; community is added the first time a command needs it.
  • Run real runtimes and tools: Node and npm, Python, OpenSSL, curl and wget, straight from the distribution. Debian 13 boots the same way as Alpine (--distro debian), with apt.
  • Write graphics and sound programs against /dev/fb0, evdev and ALSA. Try glimmer, a tiny game with sound.
  • Embed Linux in your app with a zero-dependency TypeScript SDK, published as unkernel. The same kernel file runs in Node and in every supported browser, optionally in a worker. Disks can be local ext4 images, http(s) images fetched by range, or a persistent disk in IndexedDB. The SDK is MIT-licensed, and there is no closed engine or license key behind it, so you can ship it in your product and host it wherever you like.
  • Talk to the guest through terminal sessions, each with its own pty and shell, host directories and in-memory file systems mounted in the guest, vsock byte streams and zero-copy shared memory, with no network in between.
  • Script and test: the CLI types input on a schedule, stops on a timeout, and reports how the guest ended in its exit code.

🌐 Try it in the browser

Open unkernel.dev. A shell appears after a download of about 10 MB. Your changes are saved in the browser, and the status icon opens options, diagnostics, and export or reset for your disk. Ctrl-A n (or ⌘A n on a Mac) or + on the status line opens another terminal window with its own shell, up to 9; Ctrl-A and a digit switches.

The page takes a few URL parameters:

Parameter Does
?mem=512 Guest memory in MiB
?append=... Extra kernel command line
?net=0 Boot without a network
?wisp=wss://... Use your own Wisp proxy
?jit=0 Interpreter only
?data=0 No persistent disk, a fresh system every time
?worker=0 Run the kernel on the page's thread (default: in a Web Worker where the page is cross-origin isolated)
?cpus=2 Boot on that many CPUs, each in a Web Worker (default: half the device's threads, up to 4 on desktops and 2 in Firefox, one on phones, in Safari and on iOS, where the page has the SMP kernel and is cross-origin isolated; ?cpus=1: one CPU)
?gl=0 No guest GL (on by default on Debian: the guest's Mesa renders through your browser's WebGL2, see below)

On Debian the guest gets a GPU (/dev/dri, Options, Guest GL): Mesa's virgl driver draws through your browser's WebGL2. The renderer behind it is downloaded only when a guest program first uses GL; the status panel's Guest GL row then names the GPU (a software renderer such as SwiftShader is flagged). Mesa is installed in the guest, not shipped:

sudo apt-get install -y mesa-utils libegl-mesa0 libgles2 kmscube
eglinfo -B -p gbm                 # OpenGL ES renderer: virgl (<your GPU>)
kmscube                           # on the display (Enter ends it)
sudo apt-get install -y xvfb xauth glmark2-es2-x11
xvfb-run -a -s "-screen 0 640x480x24" glmark2-es2   # frame rates

Wayland apps show as windows on the page: wland foot (or the launcher's foot tile) starts wland's relay in the guest and runs the app against it; wland's compositor runs in the page and reads the app's pixels straight from guest memory. The status line's desktop icon (Ctrl-A w) switches between the windows and the terminal.

sudo apt-get install -y foot fonts-dejavu-core
wland foot

Browsers can't open raw TCP sockets, so the page reaches the internet through a Wisp proxy. The default one accepts only known origins, so if you host the page somewhere else, point ?wisp= at your own proxy.

💻 Run it from the terminal

npx unkernel

This boots Alpine, with networking over your host's sockets. Press Ctrl-] to quit. The package holds the kernel and a small base system; the first run downloads the Alpine image (about 4 MB) from the GitHub release of your version and keeps it in ~/.cache/unkernel.

npx unkernel --distro debian                 # Debian 13 instead (about 57 MB, downloaded once)
npx unkernel --distro none                   # no distro: the base shell (busybox)
npx unkernel --data my-data.img              # changes persist on a /data disk, created on first use
npx unkernel --display --sound               # a framebuffer and a sound card
npx unkernel --mem 1024 --no-net             # more memory, no network
npx unkernel --mount .:/work                 # this directory at /work in the guest (:ro for read-only)
npx unkernel --forward 8000:80               # host 127.0.0.1:8000 to port 80 in the guest
npx unkernel --timeout 60 --input '{8}uname -a\n{2}poweroff\n'   # scripted: wait, type, wait, type
npx unkernel --help                          # everything else

Without --data, changes to the root file system are kept in memory and gone at exit; with it, each distro keeps its own in /data/distros/<name>/. --distro also takes an image file or an http(s) URL, and UNKERNEL_CACHE_DIR moves the download cache.

Exit codes: 0 power off, 1 halt or boot failure, 2 restart, 124 timeout, 253 kernel panic, 254 wasm trap, 255 fatal error. The CLI is built on the JavaScript SDK: --mount uses its host mounts and --forward its vm.connect().

🔍 How it works

Most "Linux in the browser" projects take one of three approaches:

  • Emulate a whole PC, kernel included. This is faithful but slow, because every syscall and page fault goes through emulated hardware.
  • Emulate the CPU and reimplement the syscalls. Programs run on an emulated CPU, often with a JIT, and a runtime answers their syscalls, with no Linux kernel at all. This is fast, but it covers only as much of Linux as the runtime implements.
  • Compile programs to wasm, and run them on a kernel without an MMU or on a runtime that provides POSIX calls. This is fast, but native programs have to be rebuilt, and fork and anything else that needs an MMU breaks or is approximated.

unkernel keeps the best of each: the real Linux kernel, running at native wasm speed, under unmodified binaries with a real MMU.

Approach Kernel User space MMU
Whole-machine emulators (v86, JSLinux, container2wasm, QEMU's wasm build) Linux, emulated unmodified, emulated emulated
Syscall emulators none: a runtime reimplements the syscalls unmodified, emulated the runtime's own
POSIX runtimes for wasm (Wasmer WASIX, WebContainers, BrowserPod) none: a runtime provides the syscalls rebuilt for wasm, or JavaScript none
Linux without an MMU (linux-wasm, tombl/linux, WasmLinux (LKL)) Linux, native wasm rebuilt for wasm none
unkernel Linux, native wasm unmodified aarch64, emulated real page tables

The kernel is compiled straight to WebAssembly. User programs run on kwemu, an aarch64 CPU written in Zig and linked into the kernel. kwemu walks the kernel's own page tables, so memory management is done by the real Linux code.

When a program makes a syscall, kwemu returns to the kernel, which handles it as native wasm. There is no emulated trap and no emulated kernel mode in between. Task switches use JSPI (WebAssembly.Suspending), so the kernel gets real stacks that it can suspend and resume.

kwemu runs blocks of guest code decoded once into compact ops (what has no op runs through a reference interpreter), and hot user code goes through a second tier: a JIT that compiles those blocks to wasm modules at run time, with output that matches the interpreter bit for bit. Benchmarks shows what each tier costs.

Devices are small paravirtual drivers that talk to the JavaScript host: block (kwblk), network (kwnet, with a user-mode TCP/IP stack in JS), display, input and sound (kwfb, kwinput, kwsnd), vsock (kwvsock) and shared memory (kwshm).

📊 Benchmarks

The design helps most with syscalls. These were measured under Node:

In this test (2026-11-14) fork is faster than native. Pure computation is slower. kwemu's decoded-op interpreter runs integer code at about 250-300 million guest instructions per second under Node (2026-11-17), and the JIT makes real Alpine work 1.6 to 2.3 times as fast as that (2026-11-18: an ash loop 2.5 s against 4.0 s, seq 100000 | sort -r 3.1 s against 7.1 s, seq 250000 | gzip | gunzip 3.5 s against 6.5 s), which is still well behind native.

🚧 Known limits

  • The SDK and CLI boot one CPU by default; the page boots several where it can (?cpus=). A snapshot of several CPUs (SMP), and so a session suspended on the page, resumes only on as many.
  • No IPv6, no UDP beyond DHCP and DNS, no inbound network connections (vm.connect(), vm.fetch() and --forward reach guest servers over vsock instead).
  • No ptrace register sets, so strace and gdb don't work. No seccomp.
  • Code that runs only a few times (a large program's startup, such as npm's) stays on the interpreter, and FP and AdvSIMD floating point run through it even inside compiled code. Without wasm SIMD in the host engine, OpenSSL's AES and SHA paths run on the interpreter too.
  • A wasm trap in the kernel ends the session.

🧩 Use it from JavaScript

npm install unkernel
import { createKernel, fetchDistro } from "unkernel";

const vm = await createKernel({ distro: await fetchDistro("alpine") });   // Alpine, no network
vm.onOutput((bytes) => process.stdout.write(bytes));
vm.write("uname -a; poweroff\n");

const { code, kind } = await vm.exited;          // 0, "halt"

Importing unkernel picks the Node or browser entry automatically, and unkernel/node or unkernel/web selects one explicitly. The kernel ships in the package (unkernel/unkernel.wasm) and loads from next to the entry, streamed and compiled while it downloads. It carries a small base system that mounts a distro image read-only under an overlay root and runs its init; createKernel() without distro boots the base shell (busybox and unkernel's tools), which needs no download.

The distro images are not in the package. On Node, fetchDistro("alpine") (or "debian") downloads one once from the GitHub release of the package's version, checks it against the release's distros.json (size and SHA-256), keeps it in ~/.cache/unkernel (UNKERNEL_CACHE_DIR) and returns its path; nothing else in the SDK downloads anything. In the browser, host the image yourself (it is read lazily with range requests) and pass its URL:

const vm = await createKernel({ distro: "/distros/alpine.erofs" });

Changes to the root file system stay in memory, unless a persistent data disk (labelled kwdata) is attached: then each distro keeps them in /data/distros/<name>/ on it.

Add a network

import { createKernel, directBackend, wispBackend, DEFAULT_WISP_SERVERS } from "unkernel";

await createKernel({ net: directBackend() });                       // Node: host sockets
await createKernel({ net: wispBackend(DEFAULT_WISP_SERVERS) });     // anywhere: a Wisp proxy

Networking is off unless you pass net. Any object with connect and lookup methods can carry the guest's TCP and DNS, so you can write your own backend.

Add disks

import { createImageFromKwsparse, createKernel, bundledBoot, openDisk } from "unkernel/node";

const vm = await createKernel({
  distro,
  disks: [await openDisk("data.img")],           // the data disk, or any ext4 image or https:// URL
});

createImageFromKwsparse(file, template) makes a new data disk from the template the kernel carries (bundledBoot(module).datadisk). In the browser, openHttpDisk(url) keeps your writes in IndexedDB and openDataDisk() gives you the persistent data disk that the page uses. Anything that implements BlockDevice works too, and a disk of your own can be the root: cmdline: "console=hvc0 root=/dev/wda rw" with initrd: null.

Console and lifecycle

// vm.output: a ReadableStream, everything since boot and then live
vm.output.pipeTo(new WritableStream({ write: (b) => process.stdout.write(b) }));
vm.write("ls /\n");                              // or write to vm.input, a WritableStream
vm.resize(120, 40);                              // the foreground program gets SIGWINCH

await vm.sync();                                 // flush the guest's disks
console.log(vm.stats());                         // memory, disk, network and JIT counters
const { code, reason, kind } = await vm.exited;  // stop() parks it at once

Run programs

const { stdout, exitCode } = await vm.exec("uname", ["-a"]);
const { stdout: sum } = await vm.exec("sha256sum", [], { input: "hello" });

exec() runs a program on pipes and resolves with { stdout, stderr, exitCode, signal }, also for a non-zero exit. Pass encoding: "buffer" for bytes, and cwd or env as you would to child_process. On the distro images programs run as the user user (uid 1000, in /home/user), who has sudo without a password; pass user: "root" (or another name or uid) to run as someone else. The base shell is root's.

const sh = await vm.spawn();                     // a login shell on its own pty
sh.output.pipeTo(new WritableStream({ write: (b) => process.stdout.write(b) }));
await sh.write("cat /etc/alpine-release; exit\n");
console.log(await sh.ended);                     // { type: "exit", code: 0 }

spawn(file, args, { cols, rows }) runs a program on a pty, in the zigpty / node-pty shape, with resize(), kill(signal) and close() (a hangup). Run as many as you like. Keep reading output: the guest program waits while nobody does.

const gz = await vm.spawn("gzip", ["-c"], { pty: false });
gz.stderr.cancel();                              // read both outputs, or cancel one
const zipped = new Response(gz.stdout).bytes();
await new Response("hello\n").body.pipeTo(gz.stdin);   // then EOF
console.log((await zipped).length);

With pty: false the program gets pipes: stdin, stdout and stderr web streams, byte for byte.

Mount host files

import { createKernel, MemoryFs, nodeFs } from "unkernel";

const mem = new MemoryFs();
mem.onChange((c) => console.log(c.type, c.path));   // what the guest changed

const vm = await createKernel({
  mounts: {
    "/mnt/host": { "hello.txt": "hi", dir: { "a.bin": bytes }, "now.txt": () => Date() },
    "/mnt/mem": mem,
  },
});
await vm.exec("cp", ["/etc/os-release", "/mnt/mem/"]);
console.log(mem.readText("/os-release"));

const work = await vm.mount("/work", nodeFs("."), { readOnly: true });   // Node only
await work.unmount();

A file system is a plain object tree (a function is a computed file, evaluated once per open), a MemoryFs you read and write from the host, nodeFs(dir), or your own Fs: getattr, readdir and open by path, sync or async, plus whichever change methods you want. Mounts are served over 9p on vsock. Each guest write reaches the host as it happens, and a host change shows in the guest within a second.

Talk over vsock

const listener = vm.vsock.listen(5000);          // guest programs connect to CID 2, port 5000
vm.write("echo hello | kwvsock connect 5000\n");
const conn = await listener.accept();
console.log(await new Response(conn.readable).text());   // "hello\n"
conn.close();

const c = await vm.vsock.connect(6000);          // a guest program listening on port 6000
await c.writable.getWriter().write("ping");

These are byte streams with real flow control and no network in between. vsock is on unless you pass vsock: false.

const sock = await vm.connect(8000);             // TCP to the guest's 127.0.0.1:8000
await new Response("hello\n").body.pipeTo(sock.writable);   // then EOF (a half-close)
console.log(await new Response(sock.readable).text());

vm.connect(port) reaches a TCP server on the guest's loopback through the guest's kwtty, over vsock, so it needs no network. It resolves once the guest has connected (PtyError ECONNREFUSED if nothing listens) with readable and writable byte streams, half-close included, close() and closed. The CLI's --forward HOSTPORT:GUESTPORT uses it.

vm.fetch(url, init) sends an HTTP/1.1 request to a server in the guest and returns a Response whose body streams. It always connects to the guest's 127.0.0.1 at the URL's port; the host name only goes into the Host header, so vm.fetch("http://localhost:8000/") reaches a dev server listening on port 8000. fetchOver(connect, url, init) is the same client over any byte stream.

Share memory

const vm = await createKernel({ shm: true });
await vm.exec("sh", ["-c", "printf result > /dev/shm/output"]);

const output = await vm.shm.open("output");      // a file a guest program made
const data = await output.read();
const views = output.views();                    // zero-copy, until the kernel runs again

const input = await vm.shm.create("input", 1 << 20);   // /dev/shm/input in the guest
await input.write(0, bytes);

/dev/shm exists once the guest's init has mounted it, so wait for the guest before create() (an exec() waits for it). openId(id) opens a memfd that a guest program exported through /dev/kwshm. views() and readSync() work where vm.shm.inPlace is true: inline, and in worker mode with several CPUs and shared memory (cross-origin isolated pages, Node); elsewhere read() crosses to the kernel's worker.

Display, input and sound

import { createKernel, domCodeToLinux, pcmToFloat32 } from "unkernel";

const vm = await createKernel({
  display: { width: 800, height: 600 },          // the guest gets /dev/fb0
  onDisplay: (mode) => console.log(mode),        // a program opened it (its mode) or closed it (null)
  sound: { onChunk: ({ data, format }) => play(pcmToFloat32(data, format)) },
});

const frame = vm.frame();                        // RGBA, or null while nothing draws
if (frame) ctx.putImageData(new ImageData(frame.data, frame.width, frame.height), 0, 0);

addEventListener("keydown", (e) => {
  const key = domCodeToLinux(e.code);
  if (key && vm.evdev.keyboardOpen) vm.evdev.key(key, true);
});

evdev also has button(), move(), moveTo() and wheel() for a mouse or tablet. onInput tells you when a program opens the keyboard and mouse; until then, send keys to the console. readFrame() waits for a fresh frame.

GL in the guest (browsers)

const vm = await createKernel({ distro: "/distros/debian.erofs", gl: true });
await vm.gl.ready;                               // the guest is linked; the renderer loads on its first GL use
await vm.exec("sudo", ["apt-get", "install", "-y", "mesa-utils", "libegl-mesa0", "libgles2"]);
const r = await vm.exec("sh", ["-c", "GALLIUM_DRIVER=virpipe LIBGL_ALWAYS_SOFTWARE=1 eglinfo -B -p surfaceless"]);

The guest's Mesa (Debian; its virpipe driver) renders through virglrenderer compiled to wasm (virgl.wasm, fetched only with gl, and only on the guest's first GL use; vm.gl.status tells, vm.gl.load() starts it, and gl: { eager: true } loads it before the boot so that a failure shows up front) on one WebGL2 context of the page, and gets its frames back by readback: GL 2.1 and GLES 3.0, surfaceless or under Xvfb. Node has no WebGL, so there gl is ignored with a log line.

With gpu: true as well (and a kernel with kwvirtio), the guest gets a virtio-gpu device with 3D on the same renderer: stock Mesa finds /dev/dri/renderD128 and card0 (driver virtio_gpu) and renders through it with no variables set, and a KMS client's frames (kmscube, glmark2-es2-drm, a Wayland compositor) come from the renderer's texture:

const vm = await createKernel({ distro, gl: true, gpu: true, display: { width: 1280, height: 720 } });
// per animation frame: the scanout's latest frame, no readback (null: no GL client on it)
if (vm.gl.gpu.drawFrame(ctx) === null) { /* show vm.frame() as above */ }
// the window resized: a hotplug with a new preferred mode, which KMS clients may take
vm.updateDisplaySize({ width: 1600, height: 900 });

Run it in a worker

const vm = await createKernel({
  worker: true,
  distro,                                        // a path or URL
  net: { kind: "net", backend: { kind: "direct" } },
  disks: [{ kind: "file", path: "data.img" }],
});

The kernel runs in a worker thread or Web Worker, with the same API. Disks and the network are given as specs, which the worker builds: { kind: "file", path } on Node, { kind: "http", url } and { kind: "data", template: "bundled" } in browsers. Input and frames go through shared memory when it is available (vm.transport says). This mode is experimental.

An SMP kernel (a bundle with the SMP patch) boots on several CPUs with cpus: 4, each CPU in a thread of its own on one shared memory. In browsers that needs a cross-origin isolated page and worker: true, because a CPU blocks while it waits for another, which a page's main thread may not; webCpuBlocker() says why it cannot, and vm.stats().cpus how many CPUs the kernel got.

On a server, worker: true keeps the event loop free at no cost in speed, and cpus: 4 gets most of what more CPUs give (about 3x on parallel work; 8 or 16 add little, and each CPU adds to boot time and takes 9 MiB of guest memory). node test/profile.ts measures your host, and the page's /profile.html a browser.

Boot options and helpers

import { checkSupport, ConsoleRouter, createKernel } from "unkernel";

const support = await checkSupport();            // JSPI and the rest, before you boot
if (!support.ok) throw new Error(support.problems.join("\n"));

const vm = await createKernel({
  kernel: "./my-kernel.wasm",                    // a URL, bytes, a Response or a WebAssembly.Module
  initrd: "./initramfs.cpio.gz",                 // null: none
  cmdline: "console=hvc0 rdinit=/init",
  memoryMiB: 1024,
  jit: false,                                    // interpreter only
  onProgress: (p) => console.log(p.stage),
});

const router = new ConsoleRouter({               // kernel log lines apart from program output
  onKernelLine: (line, { important }) => important && console.warn(line),
  onUserOutput: (text) => process.stdout.write(text),
});
vm.onOutput((bytes) => router.write(bytes));

The SDK has some limits, on top of the kernel's known limits. There is no guest agent beyond terminal sessions, so you drive the guest through a terminal or its console, or over vsock with your own program. stop() doesn't shut the guest down cleanly, so prefer poweroff. Only one kernel can run per thread. Types ship as .d.mts and use the DOM's WebAssembly types, so a Node-only TypeScript project needs "lib": ["dom"] or skipLibCheck.

🛠️ Building from source

You need Linux (x86-64 or arm64), Zig 0.16, Node 24, clang 21+ with the wasm target, and the usual build tools. ./setup.sh --check lists what's missing. The first build takes about 12 minutes, most of it spent on a patched wasm-ld, and uses 5 GiB of disk.

./setup.sh              # check, then build everything
node js/cli.ts          # boot your build (Alpine from vendor/build/distro/)
pnpm install && pnpm dev   # the web page at http://localhost:8080
zig build test          # emulator tests

The build makes the kernel bundle vendor/build/bundle/unkernel.wasm and the distro images vendor/build/distro/{alpine,debian}.erofs with their index distros.json; a source checkout uses those and never downloads them. guest/README.md describes the base system and how to add a distro.

kernel/README.md maps the kernel directory and its build steps. AGENTS.md and .agents/ hold the contributor notes: the kernel, its devices and the guest image, invariants, workflows, which tests to run, and the roadmap.
