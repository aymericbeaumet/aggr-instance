There are some computer programs that claim to check every step in a proof. However, various "soundness bugs" have been reported that at least potentially allowed false statements to slip past these programs. In many cases, these bugs have been demonstrated to be exploitable.

The [list](https://cr.yp.to/proofs/falseccp.html#list) at the bottom of this page links to what appear to be reports of soundness bugs for various important proof-checking programs, sorted in increasing order of the number of reports. This list includes many more soundness bugs for these programs than the bugs mentioned in [2026 Paulson](https://lawrencecpaulson.github.io/2026/01/15/Broken_proofs.html) and [2026 Stérin](https://tristan.st/blog/in_search_of_falsehood), and I don't think the list is missing any of the bugs mentioned there, but I've probably missed some reports. Please let me know about any corrections or additions.

Beware that this list doesn't include user-interface vulnerabilities. Those can have the same important effect of misleading a user as to what has been proven. See, e.g., [2016 Adams](https://link.springer.com/chapter/10.1007/978-3-319-43144-4_2).

## Advice

One standard path towards security is to minimize the complexity of the trusted computing base, which by definition is the part of the system that security reviewers need to check. From this perspective, HOL Light's proof-checking kernel is attractive because of its stability and simplicity, only 400 lines of code. But this size measurement doesn't say how carefully the HOL Light code has been reviewed, and doesn't say anything about the possibility of bugs in the underlying programming language.

Extra code can be *good* when it's test code. A battery of tests tends to catch more bugs than a single test. Running a proof through multiple proof-checking programs (preferably each in its own isolated environment) can save the day when there's a bug in one program, and is particularly easy if the checkers take the same input language for writing proofs. But it's not clear how effective this is at stopping attacks: for example, sometimes bugs are [shared by multiple checkers](https://web.archive.org/web/20260803084953/https://leanprover-community.github.io/archive/stream/270676-lean4/topic/SafeVerify-passing.20kernel.20soundness.20exploit.html).

The question ["Who watches the provers?"](https://leodemoura.github.io/blog/2026-3-16-who-watches-the-provers/) is better answered by a proof saying that a checker works correctly. A close translation of the inference rules in the HOL Light kernel, except for the rules to introduce new definitions, was already [proven in 2006](https://www.cl.cam.ac.uk/~jrh13/papers/holhol.pdf) to generate only correct theorems. That proof was also checked by HOL Light. (For readers familiar with logic: of course this assumes a large cardinal; Vω+ω is enough for HOL Light. The same paper also has a variant of the proof that skips the large-cardinal assumption, at the expense of omitting the axiom of infinity from the logic being proven.)

After more work, a clone of HOL Light called [Candle](https://cakeml.org/itp22-candle.pdf) was proven in 2022 to allow only proofs of correct theorems, as long as the CPU implements the instructions used in the Candle binary in the expected way. This proof is again computer-checked, this time in another proof-checking system, HOL4. There was also a computer-checked proof in 2022 of the correctness of a [standalone proof checker](https://research.chalmers.se/publication/532951/file/532951_Fulltext.pdf#chapter.3) for HOL proofs in OpenTheory format.

From a security perspective, it's still [concerning](https://www.cs.cmu.edu/~rdriley/487/papers/Thompson_1984_ReflectionsonTrustingTrust.pdf) to be relying on large proof-checking binaries, where the answer to why we're supposed to trust one binary is that the binary has supposedly been checked by another large proof-checking binary. I'd like to see more work on simplifying these binaries.
