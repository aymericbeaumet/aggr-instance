A new editor and processing engine for the Foveon Sensor cameras that were manufactured around 2002-2019. The existing software is either wildly slow, or does not process according to manufacturer intention. Think choosing between waiting multiple seconds after every single UI interaction to display changes, or color casts not being handled and the images looking green/magenta in different areas of the shot. One tricky bit is that the 4 different sensor architectures are all processed differently.

This weekend I am modifying the pipelines to be able to operate on downsampled sensor layers so that I can get multi shot editing as snappy as possible. If you are only displaying 500ish pixels wide, its wild to still be rendering the full 16mp image. Perfetto has been very helpful while optimizing.

Last weekend I was able to make what I feel like is a generational leap in reducing the noise from these sensors. [https://www.dpreview.com/forums/threads/foveonic-process-you...](https://www.dpreview.com/forums/threads/foveonic-process-your-x3fs-in-one-second.4869451/post-71337683)

Up next is redoing the caching/scheduling architecture to reduce the amount of overhead and to support multiplexing downsampled editing so that the images are processed within the same GPU pass instead of N passes \* M images serially.

[https://github.com/hank-bond/foveonic](https://github.com/hank-bond/foveonic)

Its slow going. When I started this near the beginning of the year the ratio between input and cached tokens costs for the interesting open weight models was less than 10 and provider side cache hit rates weren't very good, so it wasn't expensive to break the prefix to remove old things from the context and do rolling summarization to keep the prompt size down.

Now some DS v4.1 Flash providers have a ratio of 33 to 50 and >99% cache hit rates. That makes the cost of prefix cache breaks a lot higher and its definitely harder to get ahead on total cost\* of the usual approaches to context management for DS v4.1 Flash specifically.

\* - the number of requests is reduced by a factor of ~3 relative to oh-my-pi on the same benchmark; the task is long enough to require compaction once when using oh-my-pi

Definitely slower than I'd like, but it's probably worth noting there's a few things that make this demo much slower than it needs to be:

1\. There's some stuff simply not well optimized internally. Working on these now e.g. there's unnecessary internal hierarchy on all nodes that only needs to exist on a small subset (related to border boxes, overflow etc.)

2\. Eager shader compilation. There's some glass and blur shaders that are compiled on load. These really shouldn't be.

3\. Godot 4.x on the web is always pretty slow to load. Time of first contentful paint (if you ignore loading screens) is nasty across the board. Godot 4.8 upgraded Emscripten, so there's actually potential to improve this quite a bit since it's now easier to dynamically load WASM (which is what we're doing extensively here). I'm unaware of any work on this upstream though.

4\. THE BIG ONE. This demo is a bit of a monolithic beast. It doesn't just include Godot's implementation of React. You can reveal the code for any page in the demo, and edit the code live with an inline text editor. Genuinely bundled in this demo is a full TypeScript 7 implementation (based on Bun's Rust implementation) that type checks and compiles code to JS on the fly, and hot swaps components on the page live.

For the most part, this isn't designed as a performance demonstration, although there is a small section on repaints/relayouts. It's mostly just a demonstration of what's possible with the library.

Realistically, there's also the fact this is React. Its architecture is based on React Fabric (like React Native), so runtime performance should be pretty decent. But frankly, it's never going to be as performant as some alternatives — it's not really the primary goal of the project. I'm considering an alternate SolidJS front-end for improved runtime performance, but that'll do nothing for first load time, unfortunately.

pg-restic – Postgres backups to S3/B2 (or any S3-compatible storage) using restic, in one small Docker container.

I needed Postgres backups at work and at home at the same time. I tried a few existing images, but after spending time setting them up I found they shipped an older pg\_dump that couldn't back up newer Postgres versions. So I built my own.

It runs pg\_dumpall on a cron schedule and streams it straight into a restic repo, so nothing touches local disk. You get encrypted, deduplicated snapshots (hourly dumps of a mostly unchanged DB take very little extra space), retention policies, and daily pruning. If the dump fails, no snapshot is saved. It ships pg\_dumpall 18, so it can back up anything from 9.2 to 18.

I now run it in production at work, so I'll be keeping it up to date. I'm no expert, and this is the first time I'm doing something like this (putting something out there), so any feedback is welcome, especially from the database pros.

I'm working on Hale, an abstract distributed systems language.

It's a traditional systems language in the sense that you have fine control over how resources are used, but it's abstract in the sense that you have to come to an agreement with the compiler about your intent around the resources, rather than directly declaring the machinery.

It's a distributed language in the sense that there is a higher level structural abstraction in the language that situates computations of the program within a recursive graph structure. Part of that structure incorporates message broker semantics. This gives the compiler a unified view of programs across arbitrary process boundaries. The structural abstractions also enable an effects+formal verification syntax within the language, which allows programmers to codify architectural decisions that are then checked by the compiler.

The compiler itself is infrastructure aware, and the highest layer of functionality it handles is configuring the environment into which applications deploy. The single language handles everything from individual memory allocations to distributed fleet deployments.

The language is close to v1, and I'm currently building a fully distributed inference-as-a-service application with it. Arbitrary hardware/supply matched against arbitrary callers/demand in real time.

I've been working on a voxel game engine called Bonsai for ~10 years.

Probably the most interesting thing about it at the moment is the editor. The world, and most things in it, are represented as collections of SDFs. More accurately, they're density fields, but, potato-tomato. One neat thing about representing the world as SDFs is they've been thoroughly researched and documented by a guy named Inigo Quilez, and they have a lot of nice mathematical properties. For example, you can do a smooth union of arbitrary SDFs to get nice rounded contours where shapes join.

The world generator and editor operate almost entirely on the GPU. The terrain and editor pipeline is a three stage process. The first stage is user-configurable; users write an arbitrary 'shaping' shader in GLSL. The second stage is a fused stage; it does a convolution on the output of the first stage to compute a normal, runs a second user-configurable 'decoration' function, and finally applies edits. Edits are collections of SDFs that are 'compiled' from a graph structure on the CPU into a bytecode, and interpreted in the shader. The last stage runs another convolution to compute the final normal, then packs an occupancy bit, color, and normal down into a 32-bit representation, suitable for transfer back to the CPU. I expect I will expand this to include additional user-level bits for encoding biome type and GPU-driven spawning.

The entire shader pipeline is one fused 'ubershader' .. everything is bound at startup and the shader is dispatched three times, incrementing a 'Stage' uniform on each dispatch. This strategy conceptually makes the driver overhead nearly zero, and the profile agrees.

The final step in the process is giving the CPU a chance to spawn additional entities and structures after generation. This is not completely fleshed out, but the bones are there. The idea is that the results of the GPU work are passed back to the CPU, which can run arbitrary callbacks to spawn additional edits and entities. Once spawning is complete, the result is meshed using a fast binary meshing algorithm and uploaded to the GPU. I keep 16 bits of data per voxel from the GPU work, 1 bit of occupancy, and 15 bits of normal for collision response, which works out to half a megabyte per chunk. At the moment I only keep chunks which contain a piece of the world surface, and discard the rest. Surface chunks are dense, and may be compressed in the future, but keeping this amount of data scales to world sizes greater than 1B voxels cubed, which seems good enough for now.

In terms of raw performance, GPUs are ridiculous. My 3080ti mobile gets somewhere on the order of 500B-1T perlin samples per second with a naive perlin implementation. Compared to FastNoise2, that's about 1000x more, which sounds wrong since my GPU only has 35x more capacity, but, that's what my initial profiling said. That number is the marketing number; the real throughput is significantly less due to multi-stage nature of the system, but, there's a lot of headroom for improvement. For example, dropping the backing textures from 32bit to 16bit roughly quadruples performance. Since we only really care about the surface where values are near zero, I believe using 8 or 16 bit is a viable option, though this claim will require a fair amount of study to validate.

All in all, I'm pleased with how this is all working out. My original goal was to write a highly flexible system giving users both easy-to-use tools and granular control over the final output. I think I've done a fairly good job at that, and the fact it's also super fast is the cherry on top.

I've really been enjoying using Codex as a headless remote agent on my home lab. I'll often pull it up from my phone and jam on some little project when inspiration strikes.

I kept bumping into the question of how to give it access to the things it needs without leaving my private keys and other credentials on the server though.

For SSH (and sudo through pam\_ssh\_agent\_auth), I ended up building agent-auth and Agent Witness. Codex sees a normal SSH\_AUTH\_SOCK and supplies some context about why it needs a signature. If one of my Macs is available, agent-auth proxies the request to the 1Password SSH agent there. Otherwise it routes the request to Agent Witness on my phone.

Agent Witness runs as a PWA and is essentially a remote ssh-agent. The private keys are wrapped, encrypted, and stored in IndexedDB locally on the phone. The vault can only be unwrapped with a secret derived from a passkey, and all key handling and signing happens locally through the browser's Web Crypto APIs. The unwrapped keys are non-extractable CryptoKey objects (the web crypto APIs are pretty awesome!)

When a signing request comes in, the PWA gets a push notification. It shows me the reason Codex supplied, the command being run, and the key being requested. I authorize it with my passkey, the PWA signs the request, and only the resulting signature goes back to the server. The private key never leaves my phone.

[https://github.com/evanpurkhiser/agent-auth](https://github.com/evanpurkhiser/agent-auth) [https://github.com/evanpurkhiser/agent-witness](https://github.com/evanpurkhiser/agent-witness)

I also recently put together psst, which solves the related problem of handing a secret to Codex from 1Password. I give it a 1Password item-sharing link, it opens a local session where it decrypts the 1password item in memory, and Codex can inspect the available fields of the item before explicitly retrieving only the ones it needs. The CLI refuses to write secret values to a terminal, which helps keep them out of argv, shell history, and transcripts.

I’m sure I could work out a better approach where the agent absolutely cannot retrieve the secret since if it really wanted to read the secret, it could of course pipe the value into cat or whatever. The goal is to just make secret access explicit and avoid accidentally spraying credentials into places where they'll be retained. So far it’s been a very nice flow with agent browser.

I'm nearing the end of a somewhat long and arduous journey of writing a GPU-accelerated voxel terrain generator and editor.

The terrain and editor pipeline is a three stage process. The first stage is user-configurable; users write an arbitrary 'shaping' shader in GLSL. The second stage is a fused stage; it does a convolution on the output of the first stage to compute a normal, runs a second user-configurable 'decoration' function, and finally applies edits. Edits are collections of SDFs that are 'compiled' from a graph structure on the CPU into a bytecode, and interpreted in the shader. The last stage runs another convolution to compute the final normal, then packs an occupancy bit, color, and normal down into a 32-bit representation, suitable for transfer back to the CPU. I expect I will expand this to include additional user-level bits for encoding biome type and GPU-driven spawning.

The entire shader pipeline is one fused 'ubershader' .. everything is bound at startup and the shader is dispatched three times, incrementing a 'Stage' uniform on each dispatch. This strategy conceptually makes the driver overhead nearly zero, and the profile agrees.

The final step in the process is giving the CPU a chance to spawn additional entities and structures after generation. This is not completely fleshed out, but the bones are there. The idea is that the results of the GPU work are passed back to the CPU, which can run arbitrary callbacks to spawn additional edits and entities. Once spawning is complete, the result is meshed using a fast binary meshing algorithm and uploaded to the GPU. I keep 16 bits of data per voxel from the GPU work, 1 bit of occupancy, and 15 bits of normal for collision response, which works out to half a megabyte per chunk. At the moment I only keep chunks which contain a piece of the world surface, and discard the rest. Surface chunks are dense, and may be compressed in the future, but keeping this amount of data scales to world sizes greater than 1B voxels cubed, which seems good enough for now.

In terms of raw performance, GPUs are ridiculous. My 3080ti mobile gets somewhere on the order of 500B-1T perlin samples per second with a naive perlin implementation. Compared to FastNoise2, that's about 1000x more, which sounds wrong since my GPU only has 35x more capacity, but, that's what my initial profiling said. That number is the marketing number; the real throughput is significantly less due to multi-stage nature of the system, but, there's a lot of headroom for improvement. For example, dropping the backing textures from 32bit to 16bit roughly quadruples performance. Since we only really care about the surface where values are near zero, I believe using 8 or 16 bit is a viable option, though this claim will require a fair amount of study to validate.

All in all, I'm pleased with how this is all working out. My original goal was to write a highly flexible system giving users both easy-to-use tools and granular control over the final output. I think I've done a fairly good job at that, and the fact it's also super fast is the cherry on top.
